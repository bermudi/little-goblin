# Glossary

Read this only for a recurring project-specific term that is ambiguous, overloaded, unnamed, or inconsistent across code and conversation. Do not define generic engineering words, one-off phrases, or facts obvious from code.

Test the definition against concrete edge cases: “Is this still a `<term>` when …?” Sharpen the boundary or split overloaded concepts until usage is predictable, then search code and records for disagreement.

```markdown
## <Term>

<One or two sentences defining its project-specific meaning.>
```

Keep `glossary.md` flat, curated, and about domain meaning rather than implementation detail. Reconcile views and instructions that still project the old meaning.
