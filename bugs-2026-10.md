invariants in `AGENTS.md` / `DESIGN.md` (fail loud, durable writes,

## Area 1 — Durable state writes

Scope: `src/durable.ts`, `src/mail-outbox.ts`, `src/memory-queue.ts`.

### F1 — `src/durable.ts:56`: directory-fsync degradation is silent (P3, verified)

`fsyncDirectory` swallows `EINVAL`/`ENOTSUP`/`EOPNOTSUPP` with no log
line and returns normally, so `durableWriteFile`/`durableWriteBytes`
report success with rename durability absent.

- **Scenario:** if `$GOBLIN_HOME` sits on a filesystem whose directory
  fsync answers one of those errnos (some FUSE or network mounts), a
  power loss after any whole-file write can roll the rename back —
  boot then reads stale config/auth/state — and `goblin.log` contains
  zero evidence the ritual ever degraded, because the degrade path
  never logs. The degradation itself is a documented choice (the
  docstring); the silence violates the fail-loud bar the same file
  otherwise meets (short writes throw, close-reported EIO throws,
  failed renames clean up and throw — all covered in
  `src/durable.test.ts`).
- **Severity:** P3 — observability gap on an exotic-filesystem path;
  no live breakage on a normal ext4/tmpfs home.

**Checked and cleared in this area:** whole-file writes all route
through `durable.ts` (config, edit/write, fetch, script, sandbox
export, catalog cache, codex auth, whistle artifacts, harness trust,
delegation archives); `log.ts` appends one serialized JSONL record per
`appendFileSync`; `mail-outbox.ts` uses WAL + `busy_timeout` (verified
`journal_mode=wal` engages via `exec`, and bun:sqlite's default
`synchronous=FULL` exceeds the `NORMAL` minimum); `conversation.ts`
`append()` enqueues retention inside the same transaction (the
contract `memory-queue.ts`'s header demands); `memory-queue.ts`
quarantines undecodable rows instead of stalling the drain, and its
`update()` CAS throw is caught and logged per drain by
`startMemoryWorker`. `expireDue`'s `this.decide`/`this.get` is only
ever invoked as a method call (`src/tg/mail-approval.ts:565`), so the
destructuring hazard is latent, not live. `memoryQueue.get()` and
`tickNow()` have no production callers.

## Area 2 — Concurrency/lifecycle

Scope: `src/scheduler.ts`, `src/mail-watcher.ts`,
`src/delegation-lifecycle.ts`.

### F2 — `src/delegation-lifecycle.ts:237` (+ `src/index.ts:952,1000`): in-flight lifecycle ops are not joined at shutdown; boot recovery then kills a live agent (P2, verified)

`stopTicker` joins only the ticker scan (`current`); `launch`/`send`/
`answer`/`stop` promises are untracked. Shutdown (`src/index.ts:952`)
awaits just that scan, then closes the stores (`:1000`) and exits —
under a 10s budget that can also cut the whole drain (`:984-989`).
Any store touch after `delegations.close()` throws (`RangeError:
Cannot use a closed database` / `Error: Database has closed` —
reproduced against bun:sqlite directly), and both `markRunning` call
sites are unguarded (`src/delegation-lifecycle.ts:635` in `launch`,
`:780` in `send`).

- **Scenario:** if SIGTERM lands while a `launch` is between
  `bindLaunch` and `markRunning` (the whole trust-seed → startAgent →
  prompt → baseline window — seconds, and herdr lives in its own
  systemd unit so it survives the restart), the row is stranded
  `starting` — the row goes running via `markRunning` only
  (`src/delegations.ts:71`). Next boot's first scan feeds it to
  `recoverStart` (`src/delegation-lifecycle.ts:1024`), which closes
  its workspace — killing the agent that had actually started and been
  prompted — and records `failed (restarted while starting it)`: a
  wrong verdict plus destroyed in-flight work, for an op that was
  proceeding normally. The `send` variant is milder (stale
  `promptedAt`/baseline can trip the `STALL_MS` rule into one spurious
  "never started working" notice, self-healing on the next seq
  advance); a `stop` stranded the same way resurfaces as `failed
  (agent gone)` instead of `stopped`.
- **Severity:** P2 — operator-visible wrong verdict and killed agent
  work on any restart/deploy racing a launch; no data corruption (the
  row protocol itself stays consistent).

### F3 — `src/scheduler.ts:150`: `markRan` in `finally` masks the fire's error when both throw (P3, verified)

`fireScheduled` runs `fireProgram` in `try` with `markRan` in
`finally`. If the fire throws (e.g. `store.resolve` failing — the
"db gone" case pinned in `scheduler.test.ts`) and `markRan` also
throws (a `SQLITE_BUSY`/`SQLITE_FULL`/I/O blip on the programs
connection), the `finally` exception replaces the fire exception, and
the scan's `program scan failed` line carries only the storage error.

- **Scenario:** if a fire and its cursor write fail together, the log
  shows the storage error but the fire's error is lost — the line no
  longer reconstructs what the scan did, against the repo's own log
  bar. (No duplicate-fire consequence: a throwing fire never
  submitted, so the next tick's refire is correct, just late.)
- **Severity:** P3 — diagnostic masking on a double-fault path.

### F4 — `src/delegation-lifecycle.ts:691,726`: archive/restore load the whole report unbounded (P3, verified)

`send()` re-copies the previous report with
`durableWriteBytes(destination, readFileSync(destination), …)` and,
on prompt failure, `durableWriteBytes(restoreTemp,
readFileSync(archivedPath), …)` — each a whole-file `readFileSync`
plus another full copy inside `durableWriteBytes` (`Buffer.from`),
with no size cap. The same module's `readReport` caps excerpts at
16 KiB precisely so "a runaway report is never loaded whole".

- **Scenario:** if an agent writes a runaway report (a multi-hundred-MB
  dump into `report.md`), the next follow-up `send()` spikes the heap
  to ~3× the file size in one synchronous gulp; at GB scale that is an
  OOM crash of the whole process from inside a routine prompt. Realistic
  reports just cost latency/GC pain, which is why this is P3, but the
  shape contradicts the file's own stated cap.
- **Severity:** P3 — robustness gap with a crash tail risk.

**Checked and cleared in this area:** scheduler retry-ladder timers
are cleared by `stop()` and late `onDone` arms nothing (`stopped`
flag; both pinned in `scheduler.test.ts`); the mail watcher joins its
in-flight scan on `stop()` (pinned in `mail-watcher.test.ts`) and a
post-shutdown submit returns `false` so the checkpoint is held, never
skipped; the delegation ticker joins its scan; `recoverStart`
transitions in `finally` so a notice miss can't strand a `starting`
row invisibly. No double-start path exists in production (each starter
is called once in `index.ts`), so the absent double-start guards have
no live trigger.

## Area 3 — Boundary hygiene

Scope: everything under `src/` except `src/tg/` (grammy), plus
swallowed exceptions anywhere.

### F5 — `src/wake.ts:11,18,36` + `src/index.ts:436`: grammy `Api` leaks out of `src/tg/`; the leaked handle makes an undeadlined send (P3, verified)

`src/tg/delivery.ts:187` aliases `export type DeliveryApi = Api`
(grammy's client) "so domain modules can declare the dependency
without importing grammy" — but naming the type *is* the leak:
`WakeDeps.api`/`WakeBase.api` (`src/wake.ts:18,36`, feeding the
scheduler and delegation wakes) are grammy's full `Api` surface, and
`src/index.ts:436` calls a method on it directly:
`(id, text) => tg.bot.api.sendMessage(id, text)` as the program
tool's `sendPrivate`. No other file outside `src/tg/` imports grammy
(the one `rolling.ts` hit is a comment), and no grammy `Context`
appears outside `src/tg/`.

- **Scenario:** if Telegram's API hangs a connection (no RST, wedged
  middlebox) while a `program … hook` turn mints a hook URL,
  `sendPrivate` awaits that raw `sendMessage` forever — it is the one
  send path without `withTimeout`, which every `src/tg/` sender
  (`notify.ts`, `delivery.ts`, `mod.ts`, …) uses — wedging the turn's
  tool call and the conversation lane behind it until restart. The
  leak also keeps every grammy `Api` signature change a compile risk
  for domain modules, against `AGENTS.md`'s "only `src/tg/` knows
  grammy".
- **Severity:** P3 — boundary violation with a concrete but narrow
  hang scenario.

**Swallowed exceptions: no findings.** The closest calls were each
cleared by walking the path: `durable.ts`'s `discardTmp` (best-effort
unlink in an already-failing path; a stray randomly-named tmp is never
read back); `http/operator.ts:578` (queue hygiene — the attempt is
still returned, so the caller sees the rejection); `proc.ts:211,217`
(reader-cancel best-effort; the exit promise is separately awaited and
propagates); `tg/mod.ts:1105,532,1126` (chain hygiene — failures are
logged by `enqueueIntake`'s `intake step failed` line);
`auth.ts:156`/`transcribe-whistle.ts:117` (memo-eviction taps on
promises whose rejections still reach their awaiters);
`codex/model.ts:478`/`mail.ts:141` (error-*detail* best-effort; the
HTTP error itself still throws with status). Tool- and doctor-shaped
`catch → { error }` returns propagate to the caller by contract, not
silence. No literal empty `catch {}` or unaccounted `.catch(() =>
{})` remains anywhere under `src/`.

## Area 4 — Live observations (added 2026-10-17)

### F6 — `src/agent/transcribe.ts:254-289`: ffmpeg's segment muxer emits one segment per packet on MediaRecorder webm (P2, verified)

`segmentAudio` feeds the source straight into `-f segment
-segment_time N` without regenerating timestamps. Browser
MediaRecorder output has `duration=N/A` and packet timestamps the
muxer can't map to wall time — reproduced on a real 9 s app voice
note: **153 segments of ~59 ms each** where `-segment_time 15` on a
duration-bearing file yields one. The orchestrator then ran 153
sequential engine calls for one note.

- **Scenario:** every browser-mic note — the PWA composer's voice
  input — is a MediaRecorder webm. With a working cloud key (groq's
  `whisper-large-v3-turbo` profile, `-segment_time 900`), one note
  becomes ~150 sequential *paid* API calls and ~150 seconds of added
  latency; under whistle it is 153 model-load process spawns. The
  `MAX_SEGMENTS=240` ceiling nearly tripped on a 9-second note — a
  slightly longer one refuses the transcription outright.
- **Fix candidates:** regenerate timestamps before segmenting
  (`-fflags +genpts` / `asetpts=PTS-STARTPTS`), or probe duration and
  skip segmentation entirely when the file sits under the engine's
  seconds cap. Verify on a real MediaRecorder capture, not just
  ffmpeg-generated webm.
- **Severity:** P2 — silently multiplies paid calls and latency on
  every PWA voice note, and near-misses the segment ceiling on notes
  far shorter than the documented ~1 h 52 m capacity.

## Triage

Fix **F2** first: it is the only finding where a routine operation
(any deploy or restart landing inside a launch's seconds-wide herdr
window) destroys live work and records a wrong terminal verdict, and
the repair is small and local — track in-flight lifecycle ops (or
checkpoint launch progress on the row) so shutdown either joins them
or boot recovery can tell "died before start" from "was started and
prompted". Everything else is P3 hardening: F5's seam-narrowing and
F1's degrade-path log line are each a few lines, F3 wants a
catch-log before the `finally`, and F4 wants a streaming or capped
copy — all worth doing, none urgent, and none blocking on another.
